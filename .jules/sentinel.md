## 2024-05-24 - Remove innerHTML usage for DOM manipulation
**Vulnerability:** DOM-Based Cross-Site Scripting (XSS) risk via `innerHTML`.
**Learning:** The codebase generally used safe DOM APIs (`document.createElement`, `textContent`) for dynamic content rendering, but fell back to `innerHTML` for static error/empty state messages. While the strings were currently hardcoded, this established a vulnerable pattern that could be easily copied or modified to include user input or external data in the future.
**Prevention:** Strictly enforce the use of `document.createElement`, `textContent`, and safe DOM manipulation methods across the entire codebase, even for seemingly static HTML snippets. Use `.textContent = ''` to clear child nodes instead of `.innerHTML = ''`.
## 2024-05-24 - Validate localStorage schema to prevent Client-Side Injections
**Vulnerability:** Untrusted/Unvalidated `localStorage` data deserialization.
**Learning:** Directly assigning `JSON.parse(localStorage.getItem(...))` to critical app state variables without schema validation allows tampered local state to cause application crashes, logic bypasses, or prototype pollution if object structures are blindly trusted.
**Prevention:** Always validate the structure and types of data retrieved from `localStorage` before merging it into application state. Use defensive programming (e.g. `Object.create(null)`) for dictionaries mapping user input to prevent `__proto__` injection.
## 2024-05-24 - Consistent Prototype-less Object Initialization
**Vulnerability:** Partial Prototype Pollution mitigation bypass.
**Learning:** While prototype-less objects (`Object.create(null)`) were used during deserialization of state (`localStorage`), standard object literals (`{}`) were used in the initial state declaration and game reset functionality. This inconsistency meant that when the game was first loaded (without local storage) or when it was reset, the `usedCounts` dictionary was susceptible to prototype pollution and property shadowing (e.g., the `.constructor` or `.toString` properties could be invoked or collide with user-supplied keys if those keys match prototype methods). Mitigating prototype pollution requires consistent application across *all* initialization paths of dictionary-like objects storing user input.
**Prevention:** Always use `Object.create(null)` for initializing dictionary/map-like state objects that store arbitrary strings/data, enforcing it across default declarations, reset functions, and deserialization routines.
## 2024-05-24 - Mitigate Service Worker Cache Storage DoS
**Vulnerability:** Client-side Denial of Service (DoS) via Cache Storage exhaustion.
**Learning:** Service Workers that blindly cache all network responses (`event.request`) can be exploited to exhaust the user's local Cache Storage quota. An attacker (e.g. via an iframe, or simply a user generating anomalous traffic) can request the same asset with randomized query parameters (`/index.html?rand=1`, `?rand=2`, etc.). Since the Service Worker caches the exact URL string by default, this bypasses the standard cache and rapidly consumes the device's storage limits, eventually causing the application (and potentially other origins sharing the quota) to crash or fail to load assets. Additionally, blindly caching non-GET requests (POST, PUT) can lead to unexpected state caching or cache poisoning.
**Prevention:** Always explicitly check the request method (`event.request.method === 'GET'`) before intercepting and caching responses. Furthermore, strictly validate URLs being cached; explicitly reject or strip query parameters (`new URL(event.request.url).search`) from dynamic caching logic to prevent cache key proliferation and storage DoS attacks.
## 2024-05-24 - Enforce Trusted Types in Content Security Policy
**Vulnerability:** Defense in Depth: Future DOM-Based XSS via unsafe sinks.
**Learning:** While the current codebase avoids unsafe sinks like `innerHTML` and `document.write`, the risk of future regressions remains. Implementing `require-trusted-types-for 'script'` in the CSP enforces Trusted Types, neutralizing any future accidental introduction of DOM-based XSS by requiring string inputs to be explicitly validated before being rendered by the browser.
**Prevention:** Include `require-trusted-types-for 'script'` in the application's Content Security Policy. This creates an additional, browser-enforced boundary against XSS, ensuring that even if safe DOM practices are bypassed in future code modifications, string-based DOM sinks remain protected.
